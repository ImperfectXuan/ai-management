# SDD 文档组织与维护约定

> 状态：本仓库文档约定；整理日期：2026-10-10。
> SDD 指 Specification-Driven Development（规格驱动开发）。本文定义本项目的执行方式，不宣称符合某个外部认证标准，也不绑定特定工具。

## 1. 文档链路与唯一职责

需求规格 → 技术设计 → 实施任务 → 验证记录 → 进度与发布记录。每个环节引用上游文档，不复制上游全文。

| 环节 | 唯一入口 | 应回答的问题 |
|---|---|---|
| 总体需求 | [SPEC.md](SPEC.md) | 为谁解决什么问题？行为、边界与验收条件是什么？ |
| 功能变更规格 | `docs/specs/<编号>-<主题>/spec.md` | 本次新增或改变哪些需求？哪些不做？ |
| 技术设计 | [reference/ARCHITECTURE.md](reference/ARCHITECTURE.md)；功能目录内 `design.md` | 如何实现？数据契约、端差异与失败行为是什么？ |
| 实施任务 | 功能目录内 `tasks.md` | 每项任务对应哪个需求？依赖与完成条件是什么？ |
| 验证方法 | [TESTING.md](TESTING.md)、[manual-testing/](manual-testing/README.md) | 如何证明满足验收条件？ |
| 验证结果 | 功能目录内 `verification.md` | 对哪个版本、在哪个环境验证？结果与遗留问题是什么？ |
| 追踪关系 | [TRACEABILITY.md](TRACEABILITY.md) | 需求能否追到设计、任务和验证入口？ |
| 执行状态 | [PROGRESS.md](PROGRESS.md) | 做到哪里？完成证据是什么？ |
| 规划与发布 | [路线图](../ROADMAP.md)、[变更日志](../CHANGELOG.md) | 下一阶段优先级是什么？实际发布改变了什么？ |

[FEATURE_BREAKDOWN.md](FEATURE_BREAKDOWN.md) 是能力盘点与候选需求来源，不承担任务排期；README、FAQ 与各端 README 是使用说明，不定义新的需求。

`.ai-workspace/rules/` 是 AI 编码工具的共享行为约束，`.ai-workspace/memory/` 保存工作区知识；它们与产品规格职责不同。生成的 `AGENTS.md`、`CLAUDE.md` 和工具规则文件不能作为手工维护的产品规格入口。

## 2. 新功能的最小文档包

从 [specs/TEMPLATE.md](specs/TEMPLATE.md) 复制必要章节到一个功能目录。小变更可以把规格、设计、任务与验证合并为一个 `spec.md`，但保留四个章节和关联 ID；复杂变更使用四个文件。模板文件是写作参考，不是待执行的功能。

- 功能编号使用连续编号与 kebab-case，例如 `001-rule-editor`，创建前检查已有编号。
- 总体需求使用 `REQ-*`；功能需求使用 `REQ-001-*`；验收使用 `AC-*`；任务使用 `TASK-001-*`。
- 编号一旦被引用就不重用。废弃需求保留编号与原因，并链接替代需求。
- 每个需求明确适用端（CLI / TUI / Desktop）；共享文件格式不意味着三端能力相同。
- 候选需求进入开发前先补规格、设计与任务，不因出现在 TODO 中就视为已承诺交付。

## 3. 状态与推进条件

规格状态与实现状态分开记录，避免“设计已确认”被理解为“功能已交付”。

| 状态维度 | 可用状态 | 推进条件 |
|---|---|---|
| 规格 | 草案 → 已确认 → 已取代 | 已确认必须有评审者与日期；被取代需链接新规格 |
| 实施 | 待开始 → 进行中 → 待验证 → 已完成；或阻塞 / 延后 | 已完成必须关联对应版本的验证记录；阻塞写明原因 |
| 验证 | 未执行 / 通过 / 失败 / 部分通过 / 不适用 | 记录 commit、环境、命令或步骤、实际结果；不适用需理由 |

本次整理的总体规格是从既有文档提取的需求基线，不表示重新完成产品评审。既有“已完成”记录保留历史证据；仅有测试命令或验证指导不能证明当前版本通过。

## 4. 变更工作流

1. 确认需求：记录问题、适用端、边界、`REQ` 与可观察的 `AC`；列出待决问题。
2. 完成设计：引用需求 ID，描述方案、文件格式、端差异、失败行为和兼容影响。影响系统结构时更新架构文档；真实架构决策记录在 `.ai-workspace/memory/adr/`，避免建立重复决策库。
3. 拆解任务：每项 `TASK` 引用需求及验收 ID，写依赖、交付物与验证方式。排期和实施状态只在 PROGRESS 维护。
4. 实施与验证：记录实际执行的检查与结果；未执行项保持未执行，失败项记录问题与处理计划。
5. 收尾：更新追踪矩阵、能力盘点、PROGRESS；涉及用户行为变化时更新使用指南与 CHANGELOG。

仅文档改动验证相对链接、需求 ID、状态一致性及差异范围，无需执行会重写规范源或生成文件的 `aiws sync`。这类检查不能替代功能验收。

## 5. 存量文档的处理

保留现有路径，避免破坏历史引用。`superpowers/specs/`、`superpowers/plans/`、`superpowers/reviews/` 保存阶段设计、原始任务分解与评审证据；统一在文件顶部标注历史属性，并由追踪矩阵关联。后续新功能进入 `docs/specs/`。

历史计划的未勾选步骤不等于当前未实现，历史评审问题不等于仍未修复。当前状态查 PROGRESS，实际能力边界查 FEATURE_BREAKDOWN 与架构文档。历史文档中的执行指令、代码片段与依赖版本只适用于原阶段，不能直接作为当前实施任务。

## 6. 文档变更检查清单

- [ ] 需求有适用端、可观察的验收条件与明确边界。
- [ ] 设计、任务、验证能引用到同一个需求 ID。
- [ ] 未决事项、候选增强与已交付能力分开标注。
- [ ] 完成声明带版本及结果证据；历史成绩注明日期。
- [ ] 相关链接可解析，入口文档能找到本次新增或调整内容。
- [ ] 只修改应由人维护的文档，不改生成入口和运行配置。
