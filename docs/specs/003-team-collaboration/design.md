# 003 · 设计

- 规格：[spec.md](spec.md)
- 状态：草案。只记录已选产品边界和由此推出的数据契约。账号、Git 托管与技术栈见 spec §5，本文不替它们做选择。

## 1. 满足的需求

本设计满足 REQ-003-01～08。它不改 CLI 同步引擎，也不把 Desktop 的 Windows 链接策略纳入第一期验收。

## 2. 两端职责

```
macOS 应用                         团队网页与服务                 团队 Git 仓库
个人内容库                         成员 / 角色                    规则、技能、MCP
手动拉取 <------------------------ 读取当前提交
提交变更集 ----------------------> 审核差异
上报拉取回执 --------------------> 判断是否有新版本
展示提醒 <------------------------ 提醒（不带文件写入）
现有 sync -> 本机四个工具
```

网页没有到成员电脑的写通道。个人库仍是 Desktop 今天的统一内容库目录。团队规范的事实来源是该团队的 Git 仓库，不是服务里的一份平行正文。

## 3. 身份与权限

账号可以有多条团队成员关系。每条关系带团队标识和角色：成员、审核者、所有者。

草案假设同一账号在同一团队的权限取并集。成员关系不允许通过变更集修改；只有所有者调用成员管理后，成员列表才会变。

服务在提交、审核、拉取列表和回执接口上核对团队成员身份。非成员不能读取该团队仓库内容。

## 4. 变更集

变更集由 macOS 应用创建，包含：

- 目标团队。
- 一条或多条规则、技能目录或 MCP 定义的提交时内容。
- 提交时用于对照的团队仓库版本。

审核页的差异以审核时的团队仓库当前内容为基准，不以拉取回执为基准。通过时把整集写成一次新提交。写入前再次对照当前版本；目标条目已变化则整集失败，不产生只含部分条目的提交。退回不写仓库。

拒绝条件：条目类型不是规则、技能或 MCP；内容中出现 vault 文件；MCP 或其他文本里出现可判定的凭据明文。`${secret:NAME}` 占位符允许通过。服务日志不记录被拒绝内容中的疑似凭据。

网页第一期不提供团队文件编辑器。要修改团队内容，成员先在个人库改好，再提交新的变更集。

## 5. 拉取与回执

拉取只在用户于 macOS 应用中选定团队和条目后执行，写入当前个人内容库。

同名时默认另存为不冲突的新名称，原文件保持字节不变。覆盖必须是单独的确认动作，并在确认前指出将被替换的个人库路径。

每次成功拉取后，应用向账号上报回执：账号、团队、资产身份、拉到的团队版本。回执不包含资产正文，也不包含密钥。个人库随后的手工修改不更新这份回执。

可更新的判定：该回执对应的资产，在团队仓库里存在晚于回执版本、且内容不同的提交。从未上报回执的资产不产生提醒。提醒展示后，在用户手动拉取并形成新回执之前可以重复出现，但不得写入个人库。

第一期的可观察行为是应用运行中或下次启动时能看到提醒。操作系统在应用退出后投递通知仍是待决项，不影响上述判定。

## 6. 失败行为

- 提交或通过时无权：拒绝，仓库不变。
- 团队仓库不可读或不可写：变更集保持未并入，界面说明失败原因，不把本地副本标成已并入。
- 拉取时个人库不可写：不上报成功回执。
- 回执上报失败：个人库文件可以已经写好，但界面不能显示「已记录可更新跟踪」；用户可以重试上报。
- 审核通过与仓库提交之间失败：不出现半套提交。变更集保持可再次通过或退回。

## 7. 与 OpenSpec 的关系

本仓库同时有两套规划入口：

- SDD：`docs/specs/<编号>-<主题>/` 是功能需求的主文档，总体基线在 `docs/SPEC.md`。
- OpenSpec：`openspec/changes/<change>/` 用 spec-driven schema 描述一次可实施变更，包含 `proposal.md`、能力 delta、`design.md` 和 `tasks.md`。配置要求正文用中文，结构标题和 SHALL/MUST 保持英文。当前没有已归档的 OpenSpec 主规格；既有 change 是 Desktop 规则编辑、收编修复这类仓库内增量。

003 不写入 OpenSpec，原因：

- 它是新的产品面，不是某个已归档 capability 的 delta。
- 网页服务放在本仓库还是新仓库尚未决定。OpenSpec change 默认改当前仓库。
- 再写一套 proposal 会复制本目录的需求。SDD 约定每个环节不复制上游全文。

适合改用 OpenSpec 的时机：spec §5 里阻塞实施的账号、仓库托管和代码位置已经定下来，并且确定在本仓库实施。那时用一个新的 change 引用 REQ-003，而不是把本目录再搬一遍。在那之前不运行 `openspec new change`。

## 8. 兼容

不修改 `.ai-workspace/` 的现有文件契约。个人库里另存的文件仍是普通规则、技能或 MCP 文件，现有 sync 按今天的规则处理它们。团队仓库使用同一套目录约定，这样 macOS 应用可以把它读成另一份内容来源，而不发明第二种规则格式。
