## 2. 共享引擎与运行时

### 2.1 架构决策

**共享业务引擎放在 `.ai-workspace/scripts/lib/intake/`（POSIX sh + jq）**，CLI 与 Desktop 均调用它。

理由：
1. 现有 CLI 是 POSIX sh + jq + age，Desktop 通过 `vault-bridge.ts` / `execFile(aiws)` 已有调用 CLI 的先例。
2. 扫描、比较、审核计划生成、应用、复制、三方比较是纯数据处理，sh+jq 可胜任。
3. 避免 Desktop 和 CLI 各写一套规则（spec 硬约束）。
4. 不引入必需 Node 运行时到 CLI 路径。

Desktop 的 TypeScript 层负责 UI 状态、IPC 和文件对话框，通过 `execFile` 调用共享引擎并传入 JSON 参数、消费 JSON 输出。现有 `vault-bridge.ts` 模式扩展为通用 `intake-bridge`。

### 2.2 新增模块

```
.ai-workspace/scripts/lib/intake/
├── scan.sh          # 多来源只读扫描 → ScanBatch JSON
├── compare.sh       # 确定性比较 → Candidate 分类
├── plan.sh          # 审核计划生成 / 校验 / 序列化
├── apply.sh         # 入库执行（预备写入 + 提交）
├── deploy.sh        # 复制 / 同步 / 三方比较
├── identity.sh      # 资产稳定 ID、内容指纹、凭据身份
├── store.sh         # 本地记录区读写（批次、草稿、忽略、暂缓）
└── model.sh         # 模型请求组装 / 响应校验 / 脱敏
```

每个模块暴露 1-2 个主入口函数，参数为 JSON（经 stdin 或文件），输出为版本化 JSON（经 stdout）。CLI 子命令 `aiws intake <scan|compare|plan|apply|deploy|check>` 包装这些函数；Desktop 经 bridge 调用同一入口。

### 2.3 运行时约束

| 依赖 | 用途 | 缺失时行为 |
|---|---|---|
| POSIX sh | 引擎执行 | 必需 |
| jq ≥ 1.6 | JSON 读写 | 必需（现有 `has_jq` 已检查） |
| age / age-keygen | 凭据解密（仅需要凭据身份时） | 可降级：无凭据身份指纹，凭据字段标 `unidentified` |
| Node.js | **仅 Desktop UI** | CLI 不依赖 |

## 3. 数据契约与存储

### 3.1 概念模型（spec §6 要求覆盖）

八个业务概念映射到存储实体，不要求八个独立模块：

| 概念 | 存储落点 | 说明 |
|---|---|---|
| **Asset** | 总库 `assets/registry.json` + 内容文件 | 稳定 ID、类型、当前版本指针 |
| **AssetVersion** | 总库 `assets/<id>/v<N>/` | 内容 + 元数据快照 |
| **SourceOccurrence** | `registry.json` 内嵌 + 本地 `occurrences/` | 项目/工具/位置/原名/内容指纹 |
| **ScanBatch** | 本地 `intake/batches/<batch-id>/` | 扫描结果、错误、进度 |
| **Candidate** | `ScanBatch` 内嵌 | 比较后的分类候选 |
| **ReviewDecision** | 本地 `intake/decisions/<batch-id>.json` | 六种动作 + 审核状态 |
| **ApplyBatch** | 总库 `assets/history/<batch-id>.json` + 本地记录 | 执行记录、阶段结果 |
| **DeploymentBaseline** | 目标项目 `.ai-workspace/intake/baseline.json` | 接受版本 + 当时写入内容 + 绑定信息 |

### 3.2 目录布局与 Git 策略

**总库（共享，纳入 Git）：**
```
<总库>/.ai-workspace/
├── assets/
│   ├── registry.json          # 资产索引（ID、类型、当前版本、来源列表）
│   ├── <asset-id>/
│   │   ├── v1/                # 版本快照（内容 + meta.json）
│   │   │   ├── content/       # 实际文件（规则 .md / Skill 目录 / mcp.json 片段）
│   │   │   └── meta.json      # 版本元数据
│   │   └── v2/
│   └── history/
│       └── <apply-batch-id>.json
├── rules/                     # 既有规范源（不变）
├── skills/                    # 既有规范源（不变）
├── mcp/mcp.json               # 既有规范源（不变）
└── adapters/                  # 既有 mapping（不变）
```

**机器本地（不纳入 Git，加 .gitignore）：**
```
<任意项目>/.ai-workspace/
└── intake/                    # 本地记录区
    ├── batches/<batch-id>/    # 扫描批次
    │   ├── scan.json          # ScanBatch 结果
    │   └── candidates.json    # 比较后候选
    ├── decisions/             # 审核决定（含草稿）
    ├── plans/                 # 生成的审核计划
    ├── locks/                 # 执行锁
    └── baseline.json          # 复制基准（目标项目侧）
```

Git 忽略策略：
- `assets/` 纳入 Git（共享规范源的一部分）。
- `intake/` 加入 `.gitignore`（机器本地草稿/批次/锁）。
- `baseline.json` 纳入 Git（复制基准需随项目版本化，否则换机器丢失）。
- 凭据值永远不写入上述任何文件。

### 3.3 资产稳定 ID

```
asset-id = sha256( type + "|" + canonical-content-fingerprint )[:16]
```

- `type` ∈ `rule` | `skill` | `mcp`。
- `canonical-content-fingerprint` 是规范化后内容的 sha256（见 §3.4）。
- ID 在首次入库时生成并写入 `registry.json`，后续版本沿用同一 ID。
- 变体（另存变体）生成新 ID，但在 `meta.json` 的 `related` 字段登记 `parent: <原ID>`。
- 人工可读别名（规则 title / skill name / mcp server name）存 `registry.json` 的 `alias` 字段，不参与 ID 计算。

### 3.4 内容指纹（确定性比较基础）

| 类型 | 规范化规则 | 指纹材料 |
|---|---|---|
| rule | 保留正文全部字节；frontmatter 中影响适用行为的元数据（`globs`、`alwaysApply`、`tools`、`scope`、`description`）参与指纹；不删空白 | `sha256( body + semantic-frontmatter-json )` |
| skill | 目录内所有相对路径排序 + 每文件 `sha256(内容)`；链接目标路径单独记录 | `sha256( sorted(path:filehash) + link-targets )` |
| mcp | 对象键排序（`jq -S` 归一化对象键）、**数组顺序保留**（`jq -S` 不重排数组）；凭据字段替换为占位符 | `sha256( redacted-sorted-json )` |

凭据字段识别：
- 已知模式：字段名匹配 `api[_-]?key|token|password|secret|credential|authorization|auth[_-]?header|private[_-]?key|access[_-]?key`（递归所有嵌套层级）。
- 已识别凭据 → 替换为 `REDACTED`；`${secret:...}` 引用保留。
- 未知可疑字段 → 标记 `suspect` 并提示人工检查，不承诺识别所有秘密。

### 3.5 来源记录（SourceOccurrence）

```json
{
  "occurrence_id": "sha256(source-root + tool + scope + path)[:16]",
  "source_root": "/abs/path/to/project-or-home",
  "tool": "cursor",
  "scope": "project",
  "path": ".cursor/rules/foo.mdc",
  "original_name": "foo",
  "content_fingerprint": "sha256:...",
  "read_status": "ok | missing | unreadable | parse_error | unsupported",
  "read_error": null,
  "is_generated_copy": false,
  "generated_of": null,
  "link_target": null,
  "last_seen_batch": "batch-2026-10-10-..."
}
```

### 3.6 忽略与暂缓记录

```json
{
  "kind": "ignore | defer",
  "occurrence_id": "...",
  "content_fingerprint_at_decision": "sha256:...",
  "decided_at": "2026-10-10T...",
  "decided_by": "user"
}
```

- **ignore**：内容未变不重复提醒；变化后指纹不同 → 重新出现。
- **defer**：始终保留在待审核队列。
- 来源删除 / 不可访问 → 不删总库资产，不删忽略记录（保留历史）。

## 4. Schema 与接口

### 4.1 Schema 版本

所有 JSON 输出带 `"schema": "intake/v1"`。不兼容变更升 `v2`，消费方按 `schema` 字段分支。

### 4.2 CLI 接口

```
aiws intake scan     --repo <总库> --source <path>[,tool:scope]... [--manual <path>] [--json]
aiws intake compare  --repo <总库> --batch <id> [--json]
aiws intake plan     --repo <总库> --batch <id> --decisions <file> [--json]
aiws intake apply    --repo <总库> --plan <file> [--json]
aiws intake deploy   --repo <总库> --target <path> --assets <id>[,id] [--tools tool,tool] [--json]
aiws intake check    --repo <总库> --target <path> [--json]
aiws intake status   --batch <id> | --plan <id> [--json]
```

- `--json` 输出版本化 JSON 到 stdout；人类可读输出到 stderr。
- 进度事件写 stderr（`PROGRESS: {json-line}`），Desktop 桥接后转 IPC 事件。
- 取消：Desktop 发 SIGTERM 到子进程；CLI 支持 `--cancel-file <path>` 轮询。

## 5. 四工具三类资产能力矩阵

| 能力 | claude | codex | cursor | trae |
|---|---|---|---|---|

| **Skill 扫描** | ✅ `.agents/skills/` | ✅ `.agents/skills/` | ✅ `.cursor/skills/` | ✅ `.trae/skills/` |

## 6. 凭据身份与绑定

### 6.1 凭据身份指纹

原方案要求用 vault 主密钥做 HMAC。TASK-001-03 实施核实：vault 主密钥由用户口令派生（`lib/vault.sh` 的 `derive_key`），取得它必须交互认证，而扫描与比较不能要求用户输入口令；原"无 vault 时降级为 `sha256(value)[:8]`"又直接违反 spec §5.4「不能保存可离线猜测的低熵秘密摘要」。

**实际方案**：机器本地随机盐。

```
credential-identity = hmac-sha256( local-salt, normalized-secret-value )[:16]
```

- 盐为 32 字节随机值，存放 `<总库>/.ai-workspace/intake/cred-salt`，权限 600，位于 design §3.2 定义的本地记录区（不纳入 Git）。
- 只拿到仓库的人无法离线爆破低熵秘密；盐随仓库在本机存在，保证多次比较得到稳定身份。
- 覆盖顺序：`INTAKE_CRED_SALT`（测试注入）> `INTAKE_CRED_SALT_FILE` > 默认路径。
- 无盐可用时返回 `unidentified`，不以值派生的可猜测摘要兜底。
- 扫描阶段不创建盐文件（TASK-001-02 的零写入约束），因此凭据身份在比较阶段计算，比较只读来源文件。
- 指纹**不保存**秘密值本身，只保存 HMAC 截断。

### 6.2 凭据引用与绑定

- 共享资产中只存 `${secret:key_name}` 引用或 `credref:<credential-identity>`。
- 复制到目标项目时生成**绑定记录**：`{cred_ref, bound_value_source: "vault-key" | "manual", verified: bool}`。
- 未完成绑定 → 资产可存为模板，但 `deployable: false`，同步跳过。
- 不同凭据身份 → 即使脱敏显示相同也不合并（spec §5.2）。

### 6.3 本机依赖绑定

command/args/env 中的绝对路径、工作目录、数据库名标记为 `local_dependency`：

```json
{
  "field": "args[2]",
  "value_kind": "abs_path | workdir | db_name | file_dep",
  "original_value": "/home/alice/project/data",
  "bound_value": null,
  "binding_status": "unbound"
}
```

复制时必须由用户显式填写新值；AI 不猜测。未绑定 → 不标记为可运行。

## 7. 复制基准与三方比较

### 7.1 复制基准

复制时记录三份数据（§3.2 `baseline.json`）：
1. `accepted_version` + `accepted_content_fingerprint`：接受的总库版本。
2. `written_content_fingerprint`：当时实际写入项目的内容指纹（可能因绑定而与总库不同）。
3. `bound_credentials` + `bound_paths`：绑定信息。

**不能只存总库 hash**——否则无法区分"项目定制"与"绑定后的正常差异"。

### 7.2 三方比较

```
         总库当前
        /        \
  accepted      project current
  (baseline)    (实际文件)
```

| 总库 vs accepted | 项目 vs written | 结论 | 动作 |
|---|---|---|---|
| 变 | 未变 | 总库单边变化 | 提供"确认更新" |
| 未变 | 变 | 项目定制 | 提供"保留定制" |
| 变 | 变，结果不同 | 双方冲突 | 人工解决 |
| 变 | 变，结果相同 | 双方一致 | 不重复写入 |
| 未变 | 未变 | 无变化 | 跳过 |

工具生成副本漂移：单独检测（比较工具文件 vs 预期生成物），提示为"工具漂移"，不归类为项目定制。

### 7.3 受保护同步

同步前检查目标文件是否包含"未选中"内容：
- MCP：目标文件中不在本次同步计划的 server → 警告并保留（不覆盖）。
- 规则：目标文件中不在计划的手写段落 → 警告。
- Skills：非 managed 链接 / 目录 → 备份后处理。

这要求同步从"整体覆盖"改为"合并写入"或至少"影响预览 + 显式确认"。

## 8. 执行锁、幂等与崩溃恢复

### 8.1 执行锁

```
intake/locks/<scope>.lock
```

内容：`{pid, started_at, operation, batch_id}`。写入用 `O_EXCL` 语义（`set -C` + `>`）。锁过期时间 30 分钟，过期可抢占（记录抢占日志）。

锁粒度：总库 `repo.lock`；目标项目 `deploy:<target>.lock`。扫描只读不加锁。

### 8.2 幂等

- `apply` 的 `idempotency_key = sha256(plan_id + sorted action_ids)`。
- 执行前检查 `history/` 中是否已有相同 key 的成功记录 → 跳过已完成 action。
- 版本写入用临时目录 + `mv` 原子提交。
- `deploy` 按 asset + target 记录阶段状态，重试只执行未完成阶段。

### 8.3 崩溃恢复

执行流程分阶段，每阶段完成后写 `stages[]` 记录：

```
preflight → write_assets → write_registry → write_history → done
```

- 每阶段结束写 checkpoint 到 `intake/plans/<plan-id>.progress.json`。
- 崩溃后 `aiws intake status --plan <id>` 显示已完成阶段；`apply --resume` 从断点继续。
- **半途失败不能留下未报告的不一致**：write_assets 用 staging 目录，write_registry 原子替换，失败时 staging 保留供诊断。
- 回退：仅作用于该 `apply_batch_id` 实际变更的文件。回退前检查目标文件当前指纹是否等于该批次写入时的指纹——若不等，报告冲突，不覆盖。

### 8.4 并发检测

`write_registry` 前重新读取 registry 并比较版本号；不一致 → 重试（最多 3 次）或报告并发冲突。绝不静默覆盖。

## 9. 模型请求与输出契约

### 9.1 协议

OpenAI-compatible Chat Completions（`/v1/chat/completions`），支持自定义 base URL。理由：本地模型（ollama、lmstudio）和远程 API 均兼容；不预置商业模型为必需依赖。

配置存 `intake/model-config.json`（本地，不入 Git）：
```json
{
  "base_url": "http://localhost:11434/v1",
  "model": "qwen2.5:14b",
  "credential_ref": "model-api-key",
  "timeout_ms": 60000,
  "max_retries": 2
}
```

### 9.2 请求组装与确认

1. 组装前过滤：移除所有已识别凭据字段值（替换为 `credref:` 占位符）、移除 `suspect` 字段值。
2. 展示：实际发送内容（含目标服务 URL、模型名）→ 用户确认 → 发送。
3. 范围扩展或重试包含新增内容 → 重新确认。
4. 大请求分批：每批独立确认，进度显示 `batch i/N`。

### 9.3 输出契约

模型返回 JSON（`response_format: {type: "json_object"}`），schema：

```json
{
  "suggestions": [
    {
      "suggestion_id": "ai-...",
      "kind": "split|categorize|merge|variant",
      "source_occurrence_id": "...",
      "source_anchors": [
        {
          "source_occurrence_id": "...",
          "start_line": 1,
          "end_line": 10,
          "quote": "原文片段"
        }
      ],
      "proposed_content": "...",
      "category": "general|domain|project_constraint|project_context",
      "rationale": "...",
      "related_asset_ids": []
    }
  ],
  "uncovered_ranges": [
    {
      "source_occurrence_id": "...",
      "start_line": 11,
      "end_line": 50
    }
  ]
}
```

校验规则：
- `source_occurrence_id` 必须在请求范围内（顶层与每个 `source_anchors[].source_occurrence_id`、`uncovered_ranges[].source_occurrence_id`）。
- `source_anchors.quote` 必须与对应来源原文逐字匹配（锚点校验）。
- `category` 枚举值合法。
- `uncovered_ranges` 必须覆盖原文未被建议触及的部分，且携带 `source_occurrence_id`。
- 跨文件合并（`kind: "merge"`）的每个原文锚点均须携带 `source_occurrence_id`，确保可追溯到具体来源。
- 非法输出 → 整条丢弃并记录，不写总库。

### 9.4 失败与重试

| 场景 | 行为 |
|---|---|
| 未确认发送 | 不发送，保留扫描与人工状态 |
| 超时 | 中止当前批次，已完成批次结果保留 |
| 非法 JSON | 标记该批次失败，保留人工编辑 |
| 部分失败 | 显示 `batch i/N` 实际状态，不表示全量完成 |
| 重试 | 保留已编辑的审核结果，新模型结果供对照，不静默覆盖 |
| 取消 | 不批准入库 |

请求与日志不含秘密或完整敏感响应。

## 12. POSIX sh + jq + age 约束评估

| 需求 | sh+jq 可行性 | 结论 |
|---|---|---|
| 文件遍历 + 指纹 | `find` + `sha256sum`/`shasum` | ✅ |
| JSON 读写 / 合并 / 路径查询 | jq | ✅ |
| YAML frontmatter 解析 | `grep`/`awk`（现有 `get_yaml_val`） | ✅ |
| 复杂嵌套 JSON 比较 | jq `--slurp` + 自定义函数 | ✅ 可行但代码量大 |
| HMAC 凭据身份 | `openssl dgst -sha256 -hmac` 或 age 派生 | ✅ |
| HTTP 模型请求 | `curl`（Desktop 场景已有 Node） | ✅ CLI 用 curl，Desktop 可用 fetch |
| 进度 + 取消 | stderr JSON 行 + 信号/取消文件 | ✅ |
| 事务性写入 | `mv` 原子替换 + staging 目录 | ✅ |

**不引入必需 Node 运行时**。复杂 JSON 比较若 jq 代码过载，可将 `compare.sh` 的指纹计算抽为独立 awk/sed 管道，但仍不引入新运行时。

Desktop 端已有 Node，bridge 调用 CLI 时传 JSON 文件路径，避免 shell 转义问题。

## 16. 实施适配器差异记录（TASK-001-02 实测补充）

以下为 2026-10-10 扫描实现阶段发现的实际差异，更新至设计：

### 16.1 链接解析返回值

原设计假设 `intake_safe_resolve_link` 用 shell 返回码区分断链/越界。实测发现 `set -e` 下命令替换捕获非零返回值会导致脚本退出。**实际方案**：函数输出 `status|payload` 单行字符串，调用方解析，函数本身始终返回 0。

### 16.2 Skill 目录发现

原设计用 `for d in skills/*/` 只匹配目录。**实际差异**：断链（symlink 但目标不存在）不被 `*/` 匹配。改为 `for d in skills/*` + 显式过滤 `[ -d || -L ]`，确保断链被发现并报告。

### 16.3 MCP 凭据分离（jq）

`from_entries` 要求 `{key, value}` 而非 `{key, val}`。env 对象需递归处理 `API_KEY`/`TOKEN` 等敏感 key。实现为 `intake_strip_credentials`，输出 `{sanitized, credentials, suspects}`。

### 16.4 指纹计算

MCP 指纹使用脱敏后 JSON 的 sha256。`jq -S` 排序对象键但**不重排数组**（JSON 规范中数组是有序序列），因此 args 顺序自然保留。实现为 `intake_redact_for_fingerprint`（递归脱敏）→ `jq -cS`（键排序）→ sha256。

### 16.5 扫描输出结构

`sources[]` 中 `tool` 字段在 `auto` 模式下记录原始 spec 而非展开后的每个工具。`occurrences[]` 才是工具级粒度。手动来源记录 `tool: "manual", scope: "manual"`。

## 17. 实施记录：比较契约与凭据身份（TASK-001-03）

### 17.1 候选分组键

候选 = 同一"内容身份"下的全部来源。分组键：

| 类型 | 分组键 | 说明 |
|---|---|---|
| rule / skill | `type + "|" + content_fingerprint` | 内容相同即合并来源，名称不参与 |
| mcp | `"mcp|" + behavior_fingerprint + "|" + cred_fingerprint` | 以单服务器为单位；账号绑定不同即不同候选 |

MCP 不按文件分组（spec §4「MCP 以单服务器配置为单位」）。行为指纹保留 `args` 数组顺序、规范化对象键；凭据身份不进入行为指纹，单独表达。

### 17.2 标签语义

标签可同时存在（spec §5.2）。

| 标签 | 条件 |
|---|---|
| `unparseable` | 扫描 `read_status != ok`，或比较期来源已不可读 / 解析失败 |
| `duplicate` | 内容身份与总库既有规范源一致 |
| `conflict` | 同名不同内容：与总库同名资产内容不同，或同批内归一化同名而内容身份不同 |
| `changed` | 该来源存在既往决定记录，但其 `content_fingerprint_at_decision` 与当前身份不同 |
| `managed` | 来源带生成标记或 managed 链接；不据此认定总库已拥有，也不判为 `new` |
| `similar` | 归一化名称互为包含（长度 ≥ 4）且不同名；只作提示，永不据此合并 |
| `new` | 以上都不成立 |

名称归一化 = 小写 + 去除非字母数字，仅用于"同名"与"相似"判定，不参与"内容相同"判定。

### 17.3 输出结构（design §4.4 基础上新增字段）

- `suppressed[]`：已忽略且内容未变的候选，不进入待审核队列但可查（spec §5.2）。
- `credential_diff`：MCP 凭据字段的 added/removed/changed 字段名，单独表达。
- `behavior_diff`：MCP 行为字段的 added/removed/changed 路径。
- `sources[]`：候选内每个来源的 occurrence_id、名称、读取状态与位置。
- `summary` / `repo_assets`：分标签计数与总库索引规模。

### 17.4 总库既有规范源索引

不要求先建 `assets/registry.json`（属 TASK-001-04）。比较阶段直接索引：

- rules：`.ai-workspace/rules/*.md` 与 `rules/domains/*.md`
- skills：`.ai-workspace/skills/*/`
- mcp：`.ai-workspace/mcp/mcp.json` 的 `.servers`

索引键用单数 `rule`/`skill`/`mcp`，与比较项 `type` 对齐；指纹与扫描侧共用 `identity.sh` 同一批函数，避免两处语义漂移。

### 17.5 既有资产 ID

`existing_asset_id` 本轮为 `null`（registry 属 TASK-001-04）。候选 ID 采用 `sha256(type|identity)[:16]`，与 design §3.3 的资产 ID 同构，TASK-001-04 建 registry 时可直接沿用，避免二次映射。

### 17.6 决定记录（修订 design §3.6）

§3.6 以 `occurrence_id` 为键。MCP 候选跨文件、一个文件又可含多个 server，按 occurrence 记录无法区分同文件的兄弟 server。实际记录：

```json
{
  "kind": "ignore | defer",
  "candidate_id": "cand-...",
  "asset_type": "rule | skill | mcp",
  "asset_name": "fs",
  "occurrence_id": "<首来源，兼容 design 3.6>",
  "occurrence_ids": ["occ-..."],
  "content_fingerprint_at_decision": "<候选内容身份>",
  "decided_at": "...",
  "decided_by": "user"
}
```

匹配以 `candidate_id` 为准；同名但身份不同 → `changed`。忽略按候选来源组记录，暂缓仍保留在待审核队列。写入与查询由 `store.sh` 的 `intake_decision_write/list/find` 提供。

### 17.7 CLI

`aiws intake compare --repo <总库> --batch <id> [--json]`；候选写入 `<总库>/.ai-workspace/intake/batches/<batch-id>/candidates.json`，总库规范源保持只读。

### 17.8 已知限制

- 比较阶段需重新读取 MCP 来源文件以取得凭据身份（扫描阶段零写入，不能落盐）。若文件在扫描后被改动，`sources[]` 反映比较时的内容；过期复核由 TASK-001-04 的 preflight 负责。
- `similar` 只覆盖名称包含关系，不含语义相似；语义相似由 TASK-001-06/07 的 AI 建议承担。
- 规则正文差异按行输出并截断至 40 行，完整正文以来源文件为准。
- `compare.sh` 约 500 行，略高于仓库 500 行目标；分类规则为内联 jq 程序，未拆分为独立 `.jq` 文件以保持 design §2.2 的模块布局。
- 哈希工具选择显式化：`intake_sha256` 显式选择 `sha256sum` / `shasum` / `openssl`，pipeline 尾部成功不会掩盖回退失效。

## 18. 实施记录：审核计划、入库与恢复（TASK-001-04）

### 18.1 存储落点

**总库共享（纳入 Git）**

```
<总库>/.ai-workspace/
├── assets/
│   ├── registry.json                     # 资产索引（见 18.2）
│   ├── <asset-id>/v<N>/content/          # 版本内容快照
│   ├── <asset-id>/v<N>/meta.json         # 版本元数据
│   └── history/<apply-id>.json           # 执行记录（ApplyBatch）
├── rules/ skills/ mcp/                   # 既有规范源（入库写入目标）
└── adapters/<tool>/mapping.yaml          # 规则 mapping
```

**机器本地（不纳入 Git，`.ai-workspace/intake/`）**

```
intake/
├── plans/<plan-id>.json                  # 审核计划
├── plans/<plan-id>.progress.json         # 阶段检查点
├── locks/repo.lock                       # 执行锁
├── staging/<apply-id>/                   # 预备写入暂存（失败保留供诊断）
├── batches/<batch-id>/                   # 扫描与候选
└── decisions/<batch-id>.json             # 审核决定
```

回退备份落在 `assets/history/<apply-id>.backup/<rel>`，与执行记录同目录（`*.json` 扫描不受影响）。

### 18.2 registry 结构

```json
{
  "schema": "intake/v1",
  "version_counter": 3,
  "updated_at": "...",
  "assets": {
    "<asset-id>": {
      "asset_id": "...", "type": "rule|skill|mcp", "name": "...",
      "canonical_path": ".ai-workspace/rules/domains/foo.md",
      "current_version": 2,
      "versions": [{"version":1,"identity":"sha256:...","fingerprint":"sha256:...","kind":"backfill","created_at":"...","apply_id":"..."}],
      "sources": [{"occurrence_id":"...","source_root":"...","tool":"cursor","scope":"project","path":"...","identity":"..."}],
      "related": {"parent": "asset-..."} | null,
      "created_at": "...", "updated_at": "..."
    }
  }
}
```

`canonical_path` 相对总库根（与 compare 的 `existing_source.path` 同口径）。`identity` 与候选身份同构：rule/skill 为内容指纹，mcp 为 `行为指纹|凭据指纹`；`fingerprint` 为内容指纹（mcp 取行为部分）。

### 18.3 六种动作的规范源落点

| kind | 规范源写入 | 版本 | 来源关系 |
|---|---|---|---|
| `add` | `rules/domains/<rule-id>.md` / `skills/<name>/` / `mcp/mcp.json` 的 `.servers.<name>` | 新建 v1 | 登记 |
| `link` | 不写内容 | 目标未登记时补 v1（backfill） | 只登记 |
| `update` | 覆盖目标既有规范源 | 先补 v1（backfill），再新增 vN+1 | 登记 |
| `variant` | `rules/domains/<name>-<id6>.md` / `skills/<name>-<id6>/`（不与基线同名，绝不覆盖） | 新建 v1，`related.parent` 登记原项 | 登记 |
| `ignore` | 不写 | 无 | 记录所审核的来源内容身份 |
| `defer` | 不写 | 无 | 同上，候选仍在待审核队列 |

- 规则 canonical 文件名取 frontmatter `id`（无则取来源文件名），与 `register_mapping_entry` 的 `rules/domains/<id>.md` 约定一致；入库后向四个工具登记 mapping，否则下次 sync 会丢弃新规则。
- `add`/`variant` 遇到同名但内容不同的既有文件时报 `canonical_path_exists` 并拒绝覆盖；同名同内容按幂等处理（支持续跑与重复执行）。
- 目标为符号链接的 Skill 报 `canonical_is_symlink`，不做替换。

### 18.4 计划契约（补充 design §4.4）

action 增加：`asset_type`、`asset_name`、`source_identity`、`source_occurrences`、`source_paths`（含 `resolved_path`）、`labels`、`target_existing_source`、`registry_counter_snapshot`。`action_id = "act-<candidate-hex>-<kind>"`。

`unresolved` = **带 `unparseable` 或 `conflict` 标签且未被任何决定覆盖**的候选。`skipped` = 无决定且非风险标签的候选。`apply` 在 `unresolved` 非空时拒绝执行（AC-001-08：无法解析和未处理冲突不能混入写入）。无法解析项只接受 `ignore` / `defer`。

计划 `expires_at` 默认 24 小时（`INTAKE_PLAN_TTL_SECONDS`）。

### 18.5 幂等、锁与并发

- `idempotency_key = sha256(plan_id + sorted action_ids)[:16]`。执行前先算「待执行动作 = 计划动作 − 历史中同幂等键已成功应用的动作」；待执行集合为空 → 返回 `already_applied`，不写任何内容。
- 幂等判定先于 preflight：否则已完成计划的 registry 计数变化会把重跑误判为陈旧。
- 执行锁 `intake/locks/repo.lock`，`set -C` 的 O_EXCL 语义创建，TTL 30 分钟（`INTAKE_LOCK_TTL_SECONDS`）后可抢占并记 warn。锁路径存放于**全局变量** `INTAKE_APPLY_LOCK`：EXIT trap 在子 shell 退出时才触发，函数内 `local` 已离开作用域会导致漏释放。
- 并发检测：`write_registry` 前重新读取 registry，`version_counter` 与本次执行开始时不一致 → 中止且不替换 registry。

### 18.6 执行前复核与失败语义

只复核**待执行**动作：来源身份变化（`source_changed`）或目标版本快照不一致（`target_version_changed`）。任一受影响项变化即**整批中止且不写任何内容**，记录 `stages[0]=failed` 与逐项原因，计划与审核结果保留。

采用整批中止而非部分执行：apply 是一个批次提交边界，半途按旧计划写入正是 spec §5.5 要避免的「未报告的不一致」；AC-001-13 的「保留其他结果」由计划文件与决定记录保留来满足。

失败均写执行记录。差别：`write_assets` 失败时总库未改动；`write_registry` 失败时内容已落盘、registry 未更新，记录中标注 `content_written_registry_missing`，用 `--resume` 补齐。上一次为 `failed` 时要求显式 `--resume`；`cancelled` 未写入任何内容，可直接重跑。

### 18.7 崩溃恢复与回退

- 阶段序列 `preflight → write_assets → write_registry → write_history`，每阶段结果写入执行记录。
- 暂存目录 `intake/staging/<apply-id>/` 在失败时保留供诊断；内容提交后才写 registry（原子 `mv`）。
- 回退 `aiws intake rollback --apply <id>`：逐条比对 `files[].after_fingerprint` 与目标当前指纹。一致 → 从 `history/<apply-id>.backup/` 还原，或删除本批次新建的路径；不一致 → 报 `modified_after_apply` 冲突且**不覆盖**。registry 同步回退，若期间已被推进则报 `registry_advanced`。
- 回退本身写入执行记录的 `rollback` 字段（状态、时间、恢复清单、冲突清单）。回退只作用于总库本批次写入，不涉及已复制到项目的副本。

### 18.8 凭据边界

MCP 入库要求凭据值已是 `${secret:<name>}` 引用；出现原始值时拒绝该动作并报 `credential_not_reference:<字段>`，提示先用密钥管理保存再改为引用。理由：spec §5.4 禁止凭据值写入共享资产，而受控绑定流程属 TASK-001-08。本任务不发明占位凭据名，也不做明文降级。

### 18.9 测试接缝

`INTAKE_FAULT_STAGE=<preflight|write_assets|write_registry|write_history>` 命中即让该阶段失败，用于故障注入验证；未设置时不生效。并发检测用真实交错验证（监视暂存目录出现后由外部进程推进 registry），不引入额外代码接缝。

### 18.10 CLI

```
aiws intake plan     --repo <总库> --batch <id> --decisions <file> [--json]
aiws intake apply    --repo <总库> --plan <file|plan-id> [--resume] [--cancel-file <path>] [--json]
aiws intake rollback --repo <总库> --apply <apply-id> [--json]
aiws intake status   --repo <总库> --plan <plan-id> | --batch <batch-id> [--json]
```

`--json` 只输出版本化 JSON；人类可读信息走 stderr（design §4.2）。引擎函数不向 stdout 写日志，`register_mapping_entry` 的 stdout 被重定向到 stderr。

### 18.11 已知限制

- `existing_asset_id` 在候选层仍为 `null`；候选 ID 与资产 ID 由同一 `sha256(type|identity)[:16]` 派生（前缀 `cand-` / `asset-`），入库时直接沿用，不做二次映射。
- 本机依赖（绝对路径、工作目录、数据库名）的绑定属 TASK-001-08，本任务不处理。
- 回退不恢复 `assets/<id>/vN/` 版本快照目录本身；旧版本文件保留，registry 指针回退。保留旧版本不等于恢复旧版到项目（spec §5.5）。
- 入库不更新 `rules/.manifest.sha256` 与规则 CHANGELOG（属规则版本化能力，TASK-001-10 收尾时确认）。

## 19. 实施记录：Desktop 人工收编闭环（TASK-001-05）

### 19.1 分层与契约

```
renderer (向导页面) → main (类型化 IPC) → core/intake-bridge (execFile) → aiws intake ...
```

| 文件 | 职责 |
|---|---|
| `src/shared/intake-types.ts` | 与 CLI `intake/v1` JSON 一一对应的契约类型，main 与 renderer 共用 |

Desktop 不重写任何扫描/比较/审核/入库规则；一切确定性行为来自共享引擎，两端共用同一份 JSON 契约（spec 硬约束）。

### 19.2 IPC 通道

| 通道 | 入参 | 返回 |
|---|---|---|
| `intake:listBatches` | `{repoPath}` | 批次 ID 列表 |
| `intake:getBatch` | `{repoPath, batchId}` | `{scan, candidates}`（本地记录回读） |
| `intake:scan` | `{repoPath, sources[], manualFiles[], manualSkills[]}` | `ScanBatch` |
| `intake:compare` | `{repoPath, batchId}` | `CandidateSet` |
| `intake:plan` | `{repoPath, batchId, decisions[]}` | `ReviewPlan` |
| `intake:apply` | `{repoPath, planId, resume?}` | `ApplyBatch` |
| `intake:rollback` | `{repoPath, applyId}` | `ApplyBatch`（含 `rollback` 字段） |
| `intake:status` | `{repoPath, planId?\|batchId?}` | 计划与执行历史 |
| `intake:cancel` | `{repoPath}` | `{cancelled}` |
| `intake:progress`（广播） | `{repoPath, operation, message, pct}` | — |

所有通道的载荷都是对象（`repoPath` 亦然），校验失败抛 `InvalidArgument` / `UnsupportedTool`。

### 19.3 总库与来源的校验边界

- 总库以**路径**标识（不要求在已登记仓库列表里），必须已初始化 AI Workspace：`assertIntakeRepo` 检查 `.ai-workspace/scripts/aiws`，缺失抛 `AiwsNotInstalled`。
- 来源不做任何初始化或 git 要求；不存在的来源由引擎报 `status: missing` 并在 `errors[]` 给出原因（AC-001-01/02）。
- 桥接显式设置 `AIWS_ROOT=<总库>`，不依赖 CLI 的 `git rev-parse` 推断。

### 19.4 取消与进度

- `scan` / `apply` 用 `AbortController`：中止时写取消文件（CLI 轮询）并 `SIGTERM` 子进程。
- 扫描取消：不产生候选，也不批准任何资产。
- 入库取消：CLI 在提交前检查取消文件，返回 `status: cancelled` 的执行记录，内容不落盘。
- 进度来自 CLI 写往 stderr 的 `{"event":"progress",...}` 行，解析后经 `intake:progress` 广播。

### 19.5 UI 约束（对应 spec §5.3 / AC-001-08、13）

- **批量不绕过冲突**：`selectAllAsNew` 只对非风险候选批量选择「新增」，`conflict` / `unparseable` 必须逐项明确选择；界面明确提示跳过了几项。
- **未处理项阻断**：`plan.unresolved` 非空时「执行入库」按钮禁用；引擎侧同样拒绝执行，双重保险。
- **失败保留编辑**：入库失败或计划过期时保留已选动作，提示重新生成计划后再执行。
- **续跑入口**：`status: failed` 时提供「继续未完成项」（`resume: true`）与「重新生成计划」两条路径，避免用户卡死。
- **AI 入口诚实**：显示「本版本不包含模型调用能力（TASK-001-06/07 尚未实现）」，不出现假模型结果；无模型配置可完成整条闭环。

### 19.6 测试注意（组件测试加载顺序）

`react-dom` 必须在 jsdom 全局就绪**之后**加载，否则 React 的事件系统拿不到 jsdom 的 window，受控输入的 `onChange` 不会触发（`fireEvent.click` 正常，`fireEvent.change` 静默失效）。本任务的组件测试用懒加载 `await import('@testing-library/react')` 规避；既有 `app.test.tsx` 只断言渲染文本，未覆盖该问题，故未改动它。

### 19.7 已知限制

- AI 拆分、相似建议、编辑恢复未实现（TASK-001-06/07），向导中保留可解释的未配置状态。
- 本机依赖与 MCP 凭据绑定未实现（TASK-001-08）；当前入库要求凭据已是 `${secret:}` 引用。
- 来源选择沿用现有 workspace 的路径输入框模式，未接入系统目录选择对话框。
- 未做 Electron 打包验收（`npm run build` 通过；`npm run dist` 未执行）。
- 未在真实 GUI 中手工走查；UI 行为由组件测试与 IPC 处理器测试覆盖。

## 20. 实施记录：模型 API 边界与结构化建议（TASK-001-06）

### 20.1 模块划分

| 文件 | 职责 |
|---|---|
| `lib/intake/model.sh` | 配置校验、凭据获取、文本/结构化脱敏、发送范围收集、请求与批次组装 |
| `lib/intake/model-io.sh` | HTTP 发送、响应契约校验、尝试与清单记录 |
| `lib/intake/store.sh`（新增段） | AI 记录区路径与读写（`intake/ai/`） |

`model-io.sh` 是相对 design §2.2 的模块表新增的：`model.sh` 在加入校验与发送后已接近单文件上限，按「组装 / 调用」职责拆分，与 `compare.sh`→`stage.sh` 的拆法一致。

### 20.2 配置

`<总库>/.ai-workspace/intake/model-config.json`（本地，不入 Git）：

```json
{ "schema": "intake/v1", "base_url": "http://localhost:11434/v1", "model": "qwen2.5:14b",
  "credential_ref": "model-api-key", "timeout_ms": 60000, "max_retries": 2 }
```

- `base_url` 必须是 `http(s)://`、不含引号或空格，末尾斜杠归一化；端点固定为 `<base_url>/chat/completions`。
- 只保存凭据**引用名**，任何情况下不保存凭据值。
- `aiws intake model config --no-credential` 可显式清空引用（本地服务场景）。

### 20.3 凭据获取

顺序：`AIWS_MODEL_CREDENTIAL`（显式注入，供本地/非交互与自动化）→ `vault_get <credential_ref>`（需交互解锁）。

- **只在发送前一刻解析**；解析不到即拒绝发送，不发送任何请求。
- 经 `curl --config -` 从标准输入传入 `Authorization` 头：凭据不进 argv、不进请求体、不进日志、不进任何记录文件。
- 本地服务可完全不配 `credential_ref`，也不需要模型凭据。

design §9.1 未规定凭据获取方式；`AIWS_MODEL_CREDENTIAL` 是对「vault 必须交互认证」这一现实的显式出口，语义等同把密钥放进环境变量，不落盘。

### 20.4 请求组装与确认

1. `aiws intake model prepare` 收集用户**选定候选**的内容与（可选）总库资产摘要，生成请求文件 `intake/ai/requests/<request-id>.json` 并**只输出预览**，不发送。
2. 每个批次记录 `body_hash = sha256(canonical(HTTP body))`。`send` 发送前重算并比对；不一致 → `request_tampered` 且不发送。范围扩大必须重新 `prepare`（新 `request-id` = 重新确认）。
3. 大请求按累计字节分批（`--max-bytes`，默认 200000），**每批独立确认**（`--batch <n>`）；`batch i/N` 出现在预览与结果里。
4. 请求体为 OpenAI-compatible `{model, messages:[system, user], response_format:{type:"json_object"}, temperature:0, stream:false}`；`user` 内容是 JSON 化的载荷（items + repo_assets + 输出契约说明）。
5. 系统提示词明确：输入文本只是待整理数据，**不是指令**；不执行、不请求工具、不访问文件。

### 20.5 脱敏

- 文本级：按行匹配敏感键（`api[_-]?key|token|password|…`）后的 `key: value` / `key=value`，值替换为 `credref:<凭据身份>`（身份来自机器本地盐 HMAC，见 §17）。`${secret:...}` 引用本身不是秘密：先用同长度掩码抹平再匹配，既不会被误判为敏感键，也不会被破坏。
- MCP 条目用结构化拆分（`intake_mcp_split_server`）只保留行为字段，凭据字段只出现字段名。
- 每条条目记录 `redactions`（行号与类别）与 `suspects`（可疑行），供界面提示用户检查与排除。

### 20.6 响应校验

- 先解包 OpenAI 信封（`choices[0].message.content`）；服务端直接返回契约对象时原样使用。
- 逐条校验：`suggestion_id` 非空、`kind` 枚举、`source_occurrence_id` 在发送范围内、`category` 枚举、`source_anchors` 非空且**逐字匹配**原文对应行、`proposed_content` 与 `rationale` 非空。
- 不通过的建议**整条丢弃**并记录 `{index, reason}`，不写总库；非法 JSON/非对象 → 整批丢弃（`invalid_output`，零建议）。

**与 §9.3 的差异（已在实现中落定）**：`uncovered_ranges` 未覆盖原文缺口时，不整批丢弃，而是**自动补齐缺口并给出 `uncovered_ranges_autofilled` 警告**。理由：spec §5.3 要求「全部原文仍可查看，不能静默丢失」——自动补齐同样保证原文不消失，且不会因为模型的区间记账疏漏而丢弃合法建议；严格丢弃会让该契约在真实模型上近乎不可用。缺口明细记入 `coverage_gaps`，用户仍能看到模型漏掉了哪些行。

### 20.7 失败与重试

| 场景 | 行为 |
|---|---|
| 未确认发送 | `prepare` 不发请求；预览后载荷被改动 → `request_tampered`，不发送 |
| 超时 | `curl --max-time`，记 `timeout`；属于可重试失败 |
| HTTP 5xx / 网络错误 | 记 `http_error` / `network_error`；可重试 |
| HTTP 4xx | 记 `http_error`，**不重试**（配置或凭据问题，重试无意义） |
| 非法 JSON | 记 `invalid_output`，零建议；保留扫描与人工状态 |
| 部分失败 | 逐批报告 `batch i/N` 状态，不表示全量完成；成功批次不受影响 |
| 重试 | 每次尝试单独落盘 `batch-<i>.attempt-<n>.json`，**绝不覆盖**既有尝试 |
| 取消 | 取消文件存在时不发送该批，记 `cancelled`，不批准任何内容 |

### 20.8 记录与不落盘

- 请求文件保存预览时的载荷（本地记录区，含脱敏后的内容），是「已确认内容」的唯一依据。
- 结果只保存**已校验的建议**、未覆盖区间、被丢弃建议的索引与原因、请求/响应字节数与响应摘要；**原始响应不落盘**，也不整段进日志。
- 本模块不写 `assets/`、不写规范源：不存在绕过人工计划的直接入库通道。

### 20.10 测试边界

模型服务是外部边界，测试用**本机回环模拟服务**（Node `http`，随机端口，注入 `ok|badjson|badref|badanchor|badkind|nocoverage|timeout|http500|auth` 等模式），不调用真实模型服务、不产生费用。测试断言「实际发出的内容」「实际带出的凭据头」「落盘记录里有没有秘密」这些可观测事实，而不是只看返回值。

### 20.11 已知限制

- 未对真实模型服务做过验证（按任务要求只用模拟服务）。
- 文本脱敏是逐行的，不覆盖多行块标量（YAML `|`）里的秘密；这类内容会以 `suspects` 提示人工检查。

## 21. 实施记录：TASK-001-01/02 审查问题修复（2026-10-10）

### 21.1 凭据泄漏（嵌套敏感字段）

`intake_strip_credentials` 原实现只处理顶层键和 `env` 对象，`headers.Authorization` 等嵌套敏感字段未脱敏。修复为**递归处理任意深度**对象与数组；脱敏失败时返回空 `sanitized` + 全量 `suspects`，不回退为原始对象。

### 21.2 读取范围

原实现将整个 `HOME_DIR` 纳入 `allowed_roots`。修复为：
- 全局来源只授权实际选定工具的 rules/skills/mcp 路径。
- 新增 `intake_check_path_scope`：读取内容前逐级检查父目录是否有越界符号链接。
- 手动来源显式纳入范围（`dirname`）。

### 21.3 损坏 MCP 伪装成功

原实现 `parse_json_mcp || echo '{}'` 后统一 `read_status=ok`。修复为区分四种状态：`ok`（合法空配置 / 有 servers）、`parse_error`（invalid_json / missing_mcpServers_key / toml_parse_failed）、`unsupported`（不支持格式）、`unreadable`（权限/断链）。

### 21.4 手动路径空格拆分

原实现 `for mf in ${INTAKE_MANUAL_FILES}` 按 IFS 拆分。修复为换行分隔 + `while IFS= read -r`；CLI 侧同步改为换行拼接。

### 21.5 规范源扫描

新增 `intake_scan_canonical`：扫描来源 `.ai-workspace/rules/*.md`、`skills/*/`、`mcp/mcp.json`。来源类型记为 `tool: "canonical"`。与工具生成副本共存时不冲突。

### 21.6 设计契约修正

- §3.4：规则指纹纳入影响适用行为的元数据（globs/alwaysApply/tools/scope/description）；删除「低熵秘密不可离线猜测」错误描述。
- §16.4：修正 `jq -S` 说明（排序对象键、不重排数组）。
- §9.3：AI 锚点与未覆盖区间携带 `source_occurrence_id`。
- §1.3：明确预览/保存语义（扫描不改来源、不批准资产；允许保存无敏感值本地记录）。

## 23. 实施记录：TASK-001-03～06 代码审查整改（2026-10-10）

审查基准 `d086528` + 审查时未提交工作区。以下按缺陷逐项记录修复位置与结论；测试证据见
`verification.md` 运行 7 与 `.ai-workspace/scripts/test/test-intake-review-0306.sh`。

### 23.1 写入路径边界（新增 `lib/intake/paths.sh`）

原实现把规则 frontmatter `id` 直接拼进 `.ai-workspace/rules/domains/<id>.md`，`id: ../../../../escaped`
可写到总库之外；父目录是软链接时同样越界。修复：

- `intake_is_safe_segment`：单段名称不得为 `.` / `..`、不得含 `/` 或控制字符（规则 id、资产名、MCP server 名、Skill 名）。
- `intake_is_safe_rel_path`：总库相对路径不得是绝对路径、不得含 `.`/`..`/空段。
- `intake_physical_path` / `intake_within_repo`：逐级解析符号链接（含最终目标的链接链，上限 20 跳），
  要求解析后的绝对路径仍落在总库内。自实现而非 `realpath`：macOS/GNU 参数不同，且新增场景路径尚不存在。
- `intake_repo_abs_path`：校验 + 拼接的唯一入口；失败即拒绝。
- 应用点：`stage_rule` / `stage_skill` / `stage_mcp_all` / `apply_target_path` / `intake_apply_backfill_stage` /
  `intake_apply_commit_content` / `intake_apply_rollback`。错误码 `unsafe_asset_name:<name>`、`unsafe_target_path:<rel>`。
- MCP server 名与 Skill 名的校验放在「来源可读」之后、凭据门禁之前：`ignore`/`defer` 不受影响，
  不可读来源仍先报 `source_unreadable`。

### 23.2 稳定资产 ID 与目标快照（`compare.sh` / `plan.sh`）

设计 §3.3 原文即「ID 在首次入库时生成并写入 registry，后续版本沿用同一 ID」，实现却每次由**当前内容指纹**
重新推导，导致 `add → update → update` 后第二次更新产生新 ID、同一规范源出现两条登记、版本历史被拆散。修复：

- `intake_repo_index_annotate`：规范源索引条目挂上 registry 的 `asset_id` 与 `version`；`updated` 的候选因此带出
  `existing_asset_id` / `existing_version`（不再是 `null`）。
- `plan.sh` 目标解析顺序：`decision.target_asset_id` → 候选 `existing_asset_id`（registry 稳定身份）
  → 最后才是 `idmap` 派生（仅用于尚未登记的既有源）。内容指纹只用于版本与比较。
- `intake_plan_target_snapshots` 改由规范源索引构建：未登记条目用 `intake_asset_id_from_identity`（`identity.sh`，
  与入库同一规则）派生 ID，因此 Desktop 能选到「总库既有但未纳管」的项，且选到的 ID 与引擎解析一致。
- 变体仍是独立资产，`related.parent` 指向原项；原项版本不受影响。

### 23.3 目标实际内容复核（`apply.sh`）

只比 `current_version` 会漏掉「registry 未变但文件被人手改」。计划新增
`target_path` / `target_content_fingerprint` / `target_cred_fingerprint`（mcp 取行为指纹，凭据指纹单列），
preflight 用 `intake_apply_target_identity` 重算并比对，不一致记 `target_content_changed` 并整批中止。

另有暂存→提交窗口：`stage_*` 在暂存时记录 `target_before_fingerprint`，`commit_content` 落盘前再比一次，
不一致记 `target_changed_before_commit`——拒绝发生在任何覆盖动作之前。

### 23.4 提交状态持久化与续跑（`commit.sh` 拆分、`apply.sh`、`store.sh`）

原实现只在四个阶段末尾写记录，且 `write_history` 故障直接 `die`（无任何记录）；重试时把上一轮自己写下的
文件当成「既有文件」备份，损坏回退基准；`--resume` 又被自己推进的版本快照挡住。修复：

- 新增 `commit.sh`（`apply.sh` 已接近 500 行上限，按职责拆分）。
- 提交一开始就写**未完成记录**（`status: incomplete`），持久化 `files`（备份基线）、`created_versions`、
  `upserts`、`decisions`、`content_committed_actions` 与逐阶段状态；此后每次阶段推进原地更新。
- 续跑复用 `apply_id` 与已持久化的基线：`intake_apply_commit_content` 对 `baseline` 里已有的路径沿用
  `before_fingerprint` / `backup_rel`，不再重新备份；`commit_versions` 对已存在且身份一致的版本目录跳过。
- 暂存重算时把已提交的 rel 传给 `intake_apply_registry_update`（`skip_backfill`），避免把自己的写入当成
  「总库既有资产」凭空补一个初始版本。
- `preflight` 只复核本轮真正要动手的动作；`write_assets` 已完成的续跑跳过 preflight（目标已被本批次改写）。
- 状态词汇：`failed` = 未进入提交（preflight / 暂存失败）；`incomplete` = 已部分提交，必须 `--resume` 续跑；
  `ok` / `cancelled` / `already_applied` 不变。
- 故障接缝扩展为 `write_assets` / `write_assets_partial` / `write_registry` / `write_history`，覆盖
  提交前、内容部分提交、registry 未更新、终态记录未落盘四种窗口；`write_history` 现在先落盘未完成记录再返回失败。

### 23.5 回退一致性（`recover.sh`）

原实现逐文件回退时跳过冲突文件，却照旧恢复整份旧 registry，出现「内容与登记版本不一致」。修复为**先整体判定
可行性、可行才动手**：

- 扫描全部 `files[]`：当前指纹等于 `after` → 可回退；等于 `before`（或本批次新建且已删除）→ 已回退，幂等；
  否则冲突。备份缺失也是冲突。
- registry 同步判定：计数器等于 `registry_version_after` → 可回退；等于 `registry_version_before` → 已回退；
  否则 `registry_advanced` 冲突。
- 任一冲突 → 整批不动（`rollback_conflict`，记录 `conflicts` 与逐项判定），**不覆盖任何内容、不回退 registry**。
- 回退取总库执行锁；重复回退幂等；中断后重跑按同一判定继续。

### 23.6 共享资产凭据门禁（新增 `lib/intake/credentials.sh`、`stage.sh`）

人工确认不能绕过 spec §5.4。文本级扫描独立成 `credentials.sh`（`identity.sh` 本轮新增内容已接近 500 行上限，
按职责拆出「凭据文本识别与共享资产门禁」）。新增 `intake_text_credential_lines`（单文件）与
`intake_dir_credential_lines`（Skill 目录内所有文件）：识别 `key: value` / `key=value` / 块标量（`key: |` 后缩进的整段）中非空、非
`${secret:...}` 的值，只输出**行号与字段名，绝不回显值**。`intake_credential_gate_findings` 按 Rule / Skill
适配，命中即拒绝该动作：`credential_not_reference:<file>:<line>`（MCP 为 `credential_not_reference:<字段>`，
处理边界一致）。拒绝发生在暂存之前，规范源、版本快照、备份与执行记录都不会出现明文。

不为规避错误改写用户内容——命中即拒绝并提示改为引用，不做静默删除。总库既有内容（backfill 路径）属于
「已经在库里的内容」，本任务不因它阻断入库（见 23.11）。

### 23.7 忽略决定的来源边界（`compare.sh`）

原判定按 `asset_type + 内容指纹` 匹配，忽略 A 项目的规则会连带吞掉 B 项目里从未审核过的同内容文件。修复：
忽略/暂缓决定按**实际审核过的来源组**匹配——仅当候选的**全部** occurrence 都被同身份的同种决定覆盖时才生效；
新增来源、或 A+B 联合扫描中 B 未被审核，都重新进入审核。`stale_dec` 仍按来源重叠判定，来源内容变化即重新审核。
暂缓只认同身份的 defer 决定，与忽略语义分离。

### 23.8 Desktop 六动作参数与目标选择（`intake-types.ts` / `intake-selection.ts` / `intake-args.ts` / `intake-bridge.ts` / `intake.tsx`）

- `compare` 输出新增 `repo_asset_list`（含未登记项的派生 ID），供 UI 给出真实可选项。
- `PlanDecision` 带 `target_asset_id`；校验层要求非空字符串、且只允许 `link`/`update`/`variant`，
  桥接层原样写入 decisions 文件，引擎侧再校验存在性与类型（`target_not_found` / `target_type_mismatch`）。
- 详情面板对需要目标的动作给出目标下拉（同类型、已登记优先），并展示将写入的规范源路径与是否首次纳管；
  无可选目标时明确提示该项无法执行、建议改用「新增」。
- 动作、目标或总库任一变化 → 旧计划立即作废（`useEffect` 清空 `plan`），不会留下与当前审核状态不一致的可执行计划。

### 23.9 历史查询与回退入口（`intake-args.ts` / `aiws` / `recover.sh` / `intake.tsx`）

`planId` / `batchId` 统一为**可选过滤条件**：只给总库表示查询全部执行历史与计划（`aiws intake status --repo <总库>`）。
页面不再把查询失败吞成空历史，失败时展示可操作错误与「重试」，避免回退入口凭空消失。

### 23.10 模型边界（`model.sh` / `model-io.sh` / `store.sh`）

- **多行敏感值**：脱敏按块标量整体处理。原实现只替换 `API_KEY: |` 这一行，块内正文原样进入请求体。
  现在块内每行都以同一占位符遮蔽，块值整体参与凭据身份；块内空行也保守计入。占位符值改存按编号分文件的临时目录，
  避免换行值破坏制表符分隔；`redactions[].line` 同时修正为真实行号（原先是占位符序号）。
- **类型先于索引**：校验程序先判类型再索引/遍历。`source_occurrence_id: []`、`uncovered_ranges: "oops"`
  这类畸形字段不再让 jq 报错退出、丢掉整批结果；非法建议逐条拒绝并保留合法项，非法整体结构返回可识别错误，
  校验器自身异常也返回结构化 `invalid_output`。
- **逐来源锚点**：每个 anchor 自带 `source_occurrence_id`，按各自来源校验行号与原文，支持真实的跨文件 merge；
  行号必须是整数且在来源范围内。`uncovered_ranges` 逐条校验来源与范围，非法条目丢弃并记
  `uncovered_ranges_dropped`；自动补齐的区间同样携带正确来源。系统提示、输出契约与校验器使用同一契约。
- **尝试记录跨次保留**：尝试序号接续（`intake_ai_attempt_max_seq`），新增 `send_seq` 区分「单次发送内部重试」
  与「用户再次发送」；写入用 `set -C` 的 O_EXCL 语义，并发争用同一序号时换号重试，绝不覆盖既有记录。
  `intake_model_attempt_run` 的 `body_canonical` 改为显式参数，记录里的 `body_hash` 与实际发送体保证同源。

### 23.12 已知限制

- 文本凭据门禁覆盖 `key: value` / `key=value` / 块标量；其它形式（如 JSON 一行内的引号包裹、脚本里的拼接值）
  仍以 `suspects` 提示人工检查，不宣称已全部识别。
- backfill（登记总库既有资产）会把既有内容原样纳入初始版本快照；若既有文件本身含明文凭据，属于「入库前就已
  存在」，本任务不据此阻断，也不改写用户内容。
- 回退为整批语义：任一文件冲突则整批不回退。这是为保证「内容与登记版本一致」而选择的保守策略。
- Desktop 模型配置与建议审核界面仍属 TASK-001-07；本轮只补齐非 AI 闭环的目标选择与记录查询。
