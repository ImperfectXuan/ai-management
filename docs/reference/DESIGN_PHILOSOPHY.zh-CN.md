## 核心原则

### 1. 规范核心，薄适配器

规范规则系统必须对任何特定 AI Coding 工具一无所知。每个适配器将规范规则翻译成工具原生格式，并保持在 50 行以内。

**理由**：如果适配器变厚，意味着规范表示要么不完整，要么工具格式过于分歧。无论哪种情况，问题都被提前暴露，而不是隐藏在复杂的翻译逻辑中。

### 2. 约定优于配置

默认值应覆盖 80% 的使用场景。标准需求的项目应只需一个规则文件。显式配置仅为剩余 20% 服务。

**理由**：每一个可配置选项都是用户必须做出的决策，也是必须测试的代码路径。最小化配置减少认知负担和维护面。

### 3. 渐进式披露

每个模块（规则、技能、记忆、MCP）独立可用。用户可以先只采用规则模块，不必被强制引入技能或记忆系统。

**理由**：第一天强制全部模块会产生采用阻力。项目应从规则开始，随着成熟度增长逐步添加模块。

### 4. Git 原生

一切皆文件。一切版本化。无数据库，无外部服务，无运行时依赖。

**理由**：Git 是软件项目的通用协作工具。基于 Git 构建意味着零新增基础设施、完整审计追踪，以及 AI 配置的熟悉工作流（分支、审查、合并）。

### 5. 通过 Include 实现 DRY

当工具支持文件包含（如 `@path/to/rules.md`）时，适配器使用该机制。不支持时，sync 脚本生成合并文件。

**理由**：包含机制在运行时保持单一事实来源属性。生成文件是后备方案，而非主要机制。

## 显式权衡

| 决策 | 拒绝的替代方案 | 理由 |
|---|---|---|
| 规则使用 Markdown，而非 YAML/JSON | 结构化格式 | Markdown 人类可写、AI 可读；YAML frontmatter 处理元数据 |
| sync 脚本生成文件，而非 symlink | 符号链接 | Symlink 在 Windows 上需要管理员权限，在 Git 中行为不一致 |
| 每个规则主题一个文件 | 单一巨型规则文件 | 细粒度文件支持按工具和领域选择性包含 |
| Shell 脚本用于 sync/validate | Node.js、Python | 零依赖；POSIX shell 随处可用 |
| 点前缀目录 `.ai-workspace/` | 非隐藏目录 | 默认隐藏减少 `ls` 噪音，同时编辑器可见 |

## 反模式

以下模式被明确反对：

1. **规范文件中出现工具特定规则。** 类似"告诉 Codex 使用 X"的规则违反规范层原则。规则应写为"使用 X"。适配器负责如何告知每个工具。

2. **适配器文件超过 50 行。** 如果需要复杂的适配器，说明规范表示有问题。修复抽象，而非适配器。

3. **手动编辑生成的文件。** `AGENTS.md`、`CLAUDE.md` 等是生成文件。手动编辑会产生漂移，并在下次同步时被覆盖。

4. **混用规则和记忆。** 规则规定将来怎么做。记忆记录过去决定的事。它们是不同生命周期下的不同产物。

5. **过度配置。** 如果为一个工具编写了 50 条映射条目，说明有什么地方出了问题。退一步，简化。

## 与替代方案的对比

### vs. 每个项目单独维护 AGENTS.md / CLAUDE.md

现状。开始简单，但规则在工具间分化，维护成本随每个新工具倍增。

### vs. SaaS 配置服务

某些工具提供云端同步设置。这使配置脱离版本控制，绑定特定厂商，且无法在 PR 中审查。

### vs. IDE 级别设置

IDE 设置（如 `.vscode/settings.json`）是工具特定的，不能跨编辑器转移。AI Workspace 从设计上就是编辑器无关的。

## 设计演进

这份设计哲学本身也在此仓库中版本化。随着 AI Coding 工具生态的演进，原则可能会被精炼。设计哲学的变更遵循与代码变更相同的贡献流程。
